- A 1-line data fn that string-concats SQL + SELECT * does two jobs (query build + full-schema fetch); trace to a missing parameterized-query/explicit-column boundary, not two nitpicks.
- Same line copy-pasted across branches: check if the resource is already owned by another module's lifecycle API and route through it; inlining another module's private naming convention is a boundary violation, not a copy-paste nit.
- A file "identical across N copies + a live install path": diffing sources isn't enough — check settings.json/config for which copy is actually wired in; a stale hand-copy can match by coincidence today and drift silently tomorrow.
- When a hook reminds an agent of a doc's formatting convention, point at the doc, don't re-embed the rule text — copy-pasted spec in a shell string (or repeated per-file legend) WILL drift; single-source it in the index.
- A "define X" fix that only adds the definition to the canonical doc is separable from normalizing X's usage across other files — a re-review should note if only the definition landed, not the normalization.
- When lifting local UI state to fix a resize/sync bug, check whether the lifted value serves two consumers' invariants (selection identity vs visibility/open state); one derived safe value can protect one consumer's read while leaving the other's implicit assumption unchecked.
- Refactor that removes literal content duplication (cat'ing a file into a string): also check whether the same string still spells out PROCEDURAL rules that live in the canonical doc — pointer-vs-inline applies to instructions, not just data blobs; partial de-dup leaves the exact drift risk the change meant to close.
- Comments: keep to what is absolutely necessary; code should self-document. Prefer none; when a comment earns its place (a non-obvious why, a deliberate shortcut + its ceiling), make it terse/concise — one or two lines, not a paragraph. A multi-line explainer of straightforward code is a smell.
- A style object mixing a unit-string prop with numeric-token props is not automatically inconsistent: check which Chakra scale each prop reads (space vs sizes vs fontSizes) — the correct convention can legitimately differ prop-by-prop, so forcing one numeric convention across the object can be wrong.
- A path embedded BOTH as a comment/prose reference and as a variable assignment in the same file is a second easy-to-miss copy of that spec — when auditing drift, grep the file's own comments for the value, not just sibling files.
- When a fix rationale (why X-Sync was buggy, why X-Async fixes it) is worth documenting, write it once and have sibling call-sites reference it tersely — restating the same why per occurrence is comment duplication.
- When auditing a new logger.error(...) call, check the context payload shape against the codebase dominant convention (e.g. a component key), not just the tag/signature — near-universal fields get silently dropped in copy-pasted catch blocks.
- When editing a comment that another comment cross-references by topic/keyword ("see X for the Y note"), grep for that keyword's other occurrences first — trimming the referenced wording can silently orphan the pointer.
- A single-session edit can remove both a cross-reference and its target together — grep the referenced keyword within the same diff review pass, not just against the pre-edit file.
- A "reword one line" change must be coherence-checked against every OTHER line in the same doc that narrates the same flow in passing (a Flow/steps summary line silently re-asserts the pre-reword semantics even though nobody edited it) — check sibling lines, not just the edited ones.
- When trimming a verbose comment, check whether a duplicate explanation exists elsewhere (e.g. the matching spec test) before calling the trim done — shortening one copy while leaving a second full restatement is only half the fix; deleting the duplicate (when the test name self-documents) beats adding a fragile cross-file pointer.
- When a shared rationale is single-sourced onto a callee after being dropped from the caller, check the surviving comment still uses the same variable/field name as the code path it documents — trimming for terseness can quietly swap in shorthand (`credentialId`) that diverges from the actual identifier (`providerCredentialId`) used elsewhere in the file.
- When one of two sibling methods keeps its comment and the other loses it, confirm the survivor states a non-obvious rationale (design constraint), not just a longer restatement — that asymmetry is only justified by the why.

- Same tools exposed by two entrypoints (transports/auth modes) need ONE shared definition table as sole authority from day one — hand-copying schema+description per entrypoint looks safe on commit 1 but silently drifts (it did here); both should register from the shared table and differ only in ctx resolution.

- When extracting a predicate to make it unit-testable, move it to a module with NO import-time side effects (not just out of the call site) — else the test imports the boot chain and asserts your env/peer-repos are present, not that the logic is correct; a missing-config crash then masquerades as a logic failure.
- Provably-dead code earns deletion, not preservation: a branch/guard unreachable because callers are controlled + validated upstream (e.g. a `typeof x==='string'?x:JSON.stringify(x)` ternary whose string arm never fires) should be flagged for removal, not waved through as "harmless defense." User preference: deletion over addition; unused code is cost not safety. (Exception: never flag real trust-boundary validation / data-loss guards for removal.)
- User acted on the "no service layer" flag: an inline-controller fix was rejected as "unconventional" and re-done as a dedicated service with structured errors. When a same-family sibling (biometric) has a controller→service split, treat a logic-in-controller newcomer as a real layering regression to fix, not a soft nit.
- When a refactor is submitted to fix a prior review's flagged layering violation, verify it by diffing structurally against the exact sibling file the prior reviewer cited (e.g. biometric.auth.service.ts) — confirms both the violation is gone and no new drift entered the fix.
- PARAMOUNT (per user, 2026-07-16): consistency with existing repo styles/patterns outranks a generically-better approach. Structurally diff any new file against the nearest sibling solving the same problem and flag divergences (layering/error-shape/naming/test-structure) at structural severity, not as a style nit — even when the divergent code is individually correct.

- When a diff adds a new reusable component alongside a sibling call site that hand-rolls the same behavior inline, check whether the new component's HARDCODED callbacks (onSuccess/onError), not just its existence, are what blocked reuse — the fix is usually "make callbacks prop-driven so both call sites converge," not "just import it."

- When a feature swaps implementation (native bridge replacing an RN SDK flow), the old feature's exported tested helper (isUserCancelledPasskeyError, useAddPasskey) doesn't just go unused — the new code silently RE-implements the same logic inline because it didn't know the helper existed. "Orphaned tested helper next to a fresh inline reimplementation of the same logic" is its own smell, distinct from plain dead code.

- When mirroring a native bridge across two platform SDKs, diff the exact string forwarded as the reject/reject-message, not just the method set + error code — a platform's default stringification (Swift `String(describing:)` on an error struct with a `cause` field) smuggles far more debug detail into a SHARED JS telemetry call (logger.error(error.message)) than the sibling's clean field (`e.desc`). Use the same short field on both.

- When a demo/throwaway branch swaps a button's onPress handler to a new implementation, check whether the OLD handler function itself (not just its helper imports) becomes an unreferenced dead binding — a --no-verify commit is the tell that lint would have caught it; flag the dead function as a structural finding, not a nit, even on a branch that will not merge.

- When a ceremony/ownership move deletes an old helper+test and adds a new one IN THE SAME diff, check the diff's own hunks show the old inline logic replaced by an import of the new shared helper in the same commit — that's the safe swap-implementation pattern. Only flag orphaning when the OLD helper is left importable/exported after the swap, or the new code re-derives the same logic inline instead of importing the sibling.

- Clean reuse of a promotion/verification flow: pass the existing operation discriminator (e.g. REGISTER_PHONE_NUMBER) into the shared verify method so its existing side-effect block fires, and delegate the send to the existing guarded sender — zero duplicated checks, the proven path stays the single authority.

- A shared methods generic client-facing discriminator param (e.g. verifyOtp(operation) fed straight from a GraphQL arg) can legitimately receive a DIFFERENT enum value than the calling methods own operation variable — thats using the param as defined, not an overload smell. Confirm the params existing call sites before flagging "wrong operation passed in".

- When a client-set JSON-blob field and a dedicated column both hold the same concept, a dual-source read (json ?? column) confirms a SPLIT WRITE PATH rather than fixing it; the root fix is unifying the write, but that may be out of scope when the constraint is "touch only feature X".

- When a file already uses a local idiom (`!!x`), match THAT for the same read rather than a sibling file's different idiom (`Boolean(x)`) — consistency is scoped to the nearest file when both patterns coexist in the repo.

- When extracting a self-documenting predicate to kill inline comments, drop the call-site comments too — UNLESS a surviving comment explains the delegation TARGET rationale (why route to sendOtpToNumber / why pass REGISTER_PHONE_NUMBER), which is a distinct non-obvious why, not a restatement of the predicate.

- Externally-sourced config (parameter store / secrets manager) usually terminates in the CI buildspec or deploy manifest, not just the schema + local template — easy to miss since it lives outside `src/config/`. A fallback (`config.get(x) || 'literal'`) is the right narrower construct for an endpoint with one sane default; credentials gated by an `isConfigured()` check get no default.

- A typed inline cast `as unknown as { field?: T }` replacing `as any` on a JSON-column read is individually better but DIVERGES from a repo where `as any` is the uniform idiom for that column (~10 sites) — flag the divergence as a consistency nit, but an EXPLICIT user request to kill `any` at one site overrides the idiom (don't recommend reverting to `as any`). Durable fix if ever unified: ONE shared interface/accessor on the entity, not per-call-site inline casts.

- When a diff claims to "mirror" a sibling flag, check the sibling's TEST was mirrored too, not just prod code — recurring pattern: prod faithfully copies the new field's shape but the adjacent already-existing unit test isn't extended to assert the new field, and `objectContaining`-style matchers keep the test green while the new behavior is unverified.

- When a forward-looking Joi sub-schema is split onto the PR that adds its "consumer" stub, check the stub BODY actually reads the new config path — a `resolveCreds(_platform)`-style stub can add param plumbing end-to-end (resolver→service→integration) while the body still hardcodes the old value, making the schema addition look consumed when it isn't.

- When a repo hardcodes the SAME list in several independent places (a clone/sync script, a boot script, a compose spec, a README count), a "register a new X" diff has to be checked against EVERY copy — editing one makes the thing look registered while the runtime path still uses the old set. Grep every hardcoded list literal before calling registration complete.
