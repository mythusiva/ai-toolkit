- Chakra width/height use the sizes scale, NOT the space scale. A numeric w={30} does not equal 30x the 8px space step (240px) — it resolves via theme.sizes and here collapsed to 30px. Tokenize spacing/padding/gap (space scale) freely, but leave fixed px dimensions (w/h) as strings unless a real sizes token exists. Verify any px->token swap in the browser, not by arithmetic.
- When a component switches layout at a JS media-query breakpoint (isMax576) but a child sizes with Chakra responsive objects ({base, md}), the two boundaries can silently diverge; match the Chakra key numerically to the JS threshold (here sm=576px, not md=768px).
- When reviewing a change to how a third-party client lib is called (sync->async swap, event-driven re-render), read the installed packages actual source in node_modules — it settles execution-order questions (whether an unawaited async call already had a synchronous effect) that diff-reading only guesses at.

- When a diff changes a SHARED style constant's opacity/color to fix one caller, grep every other consumer of that constant in the same render tree — an "opaque loading overlay" fix for a new flow silently regressed the pre-existing flow reusing the same style object (loadingContainer shared by biometric + passkey).
- A native component from `requireNativeComponent` (e.g. a vendor SDK's view) with NO `style`/size prop can mount at 0x0 and never run — always pass an explicit size (flex:1 or fixed) even when the view is meant to be visually hidden; an absolute-fill PARENT does not propagate size to an unstyled native child.

- A feature-flag gate is NOT a platform guard. When a native module is one-platform-only (Android-only bridge), grep every UI entry point that checks the flag and verify at least one also checks `Platform.OS` (or a bridge-availability helper) — else the other platform silently inherits a dead, always-throwing button that the flag still shows.

- When a helper's platform coverage changes (Android-only bridge → Android+iOS), grep its call sites for prose comments that assert the OLD platform scope — stale reasoning-comments compile fine and actively mislead the next reader/reviewer who trusts the comment over the implementation.
- When a plan cites an on-device "verified" build from a hand-edited/gitignored native project, diff the on-disk config against what the config-plugin/expo-build-properties layer declares — CNG drift silently narrows what was actually tested.

- When a PR deletes one helper and folds its logic into a new one, diff BOTH old and new file bodies for duplicated private builder functions (buildAttestation, buildCreationOptions, buildRequestOptions) — a consolidation is often silently happening and is worth calling out as a positive, not just checking the new file in isolation.

- Frontend source AND comments must not leak backend internals — DB table/column names, internal service/module names, queue/topic names, infra identifiers. Flag any such leak in client code or comments as info-exposure (too much information for the frontend). Keep the behavioral WHY (e.g. "revocation is enforced server-side at session creation, not here") but strip the private backend names. This fires even on a 1-line comment reword in client code.
