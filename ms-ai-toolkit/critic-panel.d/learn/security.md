- Shared data-access fn: fix the query once (parameterize + explicit columns + type-guard) — trust-boundary defense belongs where all caller paths converge.
- Refactor lifting selection into a shared index: verify the visibility gate stays at array-construction (membership), not at render-of-index; derive all views from one gated+clamped array so a single enforcement point holds. A raw index used alongside a clamped one is the leak to hunt.
- "Inline contents -> emit paths" refactor: the trust question is whether the PATH is attacker-influenced. Static/hardcoded paths make path-passing no worse than inlining, and the content's prompt-injection surface is pre-existing, not introduced by the diff.
- A client-side feature gate that only toggles UI affordance visibility (e.g. login-method buttons) is not an authz boundary — judge it on experiment/bucketing integrity and anchor the security verdict on the server-side check the button leads to.
- When a refactor lifts a security gate into a shared service, confirm the enforcement point stays singular AND that newly-validated inputs are validated BEFORE any parse/derive step consumes them — order matters as much as presence.

- When an auth ceremony moves to a third-party hosted flow that mints the session token, audit the debug/observability path too — a "temporary" full-response log of the success payload routinely ships a live bearer credential (the IdP-minted session/custom token) to the log sink. Log only non-sensitive ids.

- When an auth ceremony moves to a headless native/third-party bridge, check the bridge's return map carries the fields the DOWNSTREAM gate depends on (e.g. credentialId for revocation), not just the bearer token — "enforcement now lives at sessionLogin" is false if the discriminator never travels there. Also: bridge only what callers use — returning unused session/refresh JWTs to the JS heap needlessly exposes long-lived credentials to logs/session-replay.

- When a native bridge delegates the WebAuthn ceremony wholly to a third party that mints the session credential (vendor SDK → IdP custom token), the credentialId is structurally unavailable to the client (the ASAuthorization/CredentialManager ceremony hides which credential was used) — so any downstream gate keyed on credentialId is silently un-enforceable on that path. The fix is server-side (revoke in the IdP, or bind credentialId into the IdP→app token), NOT "add a field to the bridge map."
- Hybrid design splitting the WebAuthn ceremony (IdP) from the authz gate (local DB): verify the credential id the gate keys on is cryptographically bound to the token that established the session — a client-asserted id checked only for existence turns per-credential controls into per-user ones.

- When a WebAuthn ceremony is lifted client-side by handing the browser an IdP *user refresh token* to drive it, that token is the real authz boundary — full-session-scoped, lets the client run unlimited enrollment ceremonies at the IdP, so any server-side per-credential cap/revocation keyed on a separately-client-asserted credentialId is advisory only. Gate the token mint (OTP) and TTL/scope the token; don't rely on the post-hoc credentialId check.

- When a new auth side-path writes a value into a column another flow gates with fraud checks (VOIP/duplicate/cap), the value is only as trusted as its source; if the source is raw client input, reaching the verified state by a different door voids the door guards. Reuse the guarded ceremony (send+verify) rather than duplicating a weaker copy.

- When a verify/promotion step is guarded only by an external provider code<->identifier binding (e.g. Twilio OTP code bound to the recipient number), the guarantee is environment-conditional: any dev/test bypass (magic OTP, mock verifier) silently voids it. "Send-side checks gate promotion" holds only where the real provider is in the loop.
