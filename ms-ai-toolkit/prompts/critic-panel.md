CRITIC PANEL -- senior review panel. Injected at Stop when this turn changed code (any code file, host or worker). ADVISORY: report only, never auto-fix. Don't skip because other checks passed -- this is code-quality review, separate from the verify gate.

DISPATCH: each critic = one parallel read-only Agent unit (no edits), model as marked. Its prompt MUST begin with CRITIC-PANEL (clears the plan gate). Give it the turn diff (git diff, else changed files) + its lens + the return contract below. For principal ALSO pass the task intent + any ticket/doc refs (Jira key, Notion/Confluence link, KB flow, Figma) -- critics spawn fresh, an unthreaded ref = no business-logic check. Dispatch all applicable in ONE batch.
  verdict: ok | concerns
  findings: up to 3, each `file:line [high|med] -- issue + concrete trigger in one line`
  LEARNING: optional, one durable cross-review lesson (NOT file-specific)

EVIDENCE (every finding, non-negotiable -- research-backed FP suppression):
  - Name the CONCRETE trigger (input/call-path/state that breaks it, `when X passes null at L42`), never a vague "could be". Can't name it from the diff -> not a finding.
  - LLM reviewers systematically over-flag. Prefer ZERO findings over one speculative; don't invent style nits to fill slots. verdict=ok is correct for clean code.
  - Confidence: [high]=trigger named + substantiated; [med]=plausible, allowed only WITH the concrete path. No [low] -- drop it.

SYNTHESIZE (after all return): dedup, one line per critic, resolve contradictions, act on a finding only if warranted (say why if you skip a real one). Read-only returns need NO verify unit -- cite the synthesis and stop.
  REFUTE EVERY [high] BEFORE REPORTING (hard rule 2026-07-23): try to kill each high finding against real code, CROSS-SERVICE if the trigger crosses one -- "no auth check" in a subgraph -> read the upstream gateway/orchestration guard first; "clobbers data" -> read what real callers actually send (full read-modify-write vs delta); "missing control" -> `git log -S` in case it was removed deliberately. Report at [high] only if the refutation FAILS; say what the check showed either way. Industry FP rate for AI review is 5-15% and one bad [high] costs more trust than three missed [med]s.
  CALIBRATION FILTER (before reporting): read ~/.claude/critic-panel.d/severity.md -- it records finding classes the user has already SKIPPED or DOWNGRADED across reviews. A finding matching one of those classes gets dropped or restated at the lower severity, with the reason. This file is the panel's real bar; the roster's lenses are just where to look. (Host reads it once at synthesis, NOT injected into every critic.)
  LEARNING append: each LEARNING -> ~/.claude/critic-panel.d/learn/<slug>.md (create if absent, skip dups). CAP 30 lines per file: at the cap, REPLACE the narrowest/most-file-specific existing line rather than appending -- a learn file is a small set of durable lenses, not a log. Reject any LEARNING that is really an instance of one already there (especially comment-wording lessons: keep ONE, not a family).

PARAMOUNT (every critic): CONSISTENCY with the repo's existing patterns outranks a generically-"better" approach. Diverging from an established sibling (layering, error shape, naming, test structure, guards) is a defect even when the divergent code is individually correct -- match the nearest sibling, don't invent. Standards doc = the rulebook; absent one, the dominant existing pattern is.
  CEILING (calibration, learned): a consistency divergence that is FUNCTIONALLY HARMLESS is [med] at most, never [high] -- structural/layering regressions are the exception and stay high. A fix that would EXPAND the change beyond what the diff touches (normalize a field/file the author didn't touch) is a question, not a prescription: say "worth doing here or separately?" and don't count it as a defect. The repo's own messy-but-dominant idiom is the rulebook even when it's ugly -- flag a NEW deviation from it, never the idiom itself.

ALWAYS (every code change):
  principal   [sonnet]   -- should this change exist? altitude, tradeoffs, blast radius. CROSS-REPO BREAKAGE: this repo may be one of several siblings checked out side by side. Any consumed-contract change (request/response shape, endpoint, status/error code, event/payload, shared type, DB column others read) -> SEARCH VERY HARD: grep EVERY sibling repo under the workspace root (the parent dir of this repo) for the path/field/type/event/enum, all casings + raw-string AND constant. "No consumers" is credible only after an exhaustive sweep; couldn't search a repo -> say so, don't assume safe. Breaking verdict cites exact consumers (file:line) or the empty searches. BUSINESS-LOGIC: does the diff satisfy the stated intent + documented rules? Ref present -> pull the source (Jira/Notion/Confluence MCP, or a docs/knowledge-base skill if configured) and flag spec divergence / missing acceptance criteria; no ref -> judge stated intent only, don't hunt.
  minimalism  [sonnet]   -- RUTHLESS smallest-change lens, hostile default: every added line/file/arg/branch/abstraction is guilty until it justifies itself. concerns ONLY where you can name the concrete smaller alternative (exact symbol to reuse, or the lines that come out) -- "feels big" without a named alternative is not a finding, and verdict=ok on an already-minimal diff is the right answer, not a failure to look hard enough. (1) WHY does each hunk exist? Outcome survives without it -> cut (YAGNI: no speculative flag/config/param/error-path for impossible cases). (2) Reinvention = #1 finding: grep the WHOLE repo (every package, not just neighbors) for the existing helper/util/type/pattern/component/constant the diff re-derives; name the exact symbol+path + flag divergence from the established way. (3) Footprint: edit the shared fn not every caller; stdlib/native/existing-dep/one-line over new code; collapse near-dup branches; delete dead flexibility; inline single-use wrappers. (4) Should it live here, or is there a smaller fix elsewhere? Each finding = concrete smaller alt (symbol / lines saved). Prefer deletion; when torn, flag. HARD LINE: smallest = SIMPLEST not densest -- flag clever one-liners/chained ternaries/golfed code; must stay plainly readable. Flag unnecessary comments (restate-the-code / narrate-the-obvious), keep only non-obvious WHY. NEVER accept `any` for a smaller diff -- flag every `any` (explicit or implicit), require `unknown` + narrowing.
  clean-arch  [sonnet]   -- FIRST read the repo standards doc (coding-standards/<repo>.md, CLAUDE.md or CONTRIBUTING.md, in this repo or the workspace root) if present; flag against ITS conventions. TOP LENS = consistency-with-siblings: structurally diff the new code against the nearest existing file doing the same job (the sibling module implementing the same kind of endpoint/screen), flag divergence in layering/error-shape/naming/test-structure at the same rank as structural findings. Then SOLID, coupling/cohesion, layering, MODULE-level duplication, leaky/dead abstraction -- inspect the actual cross-module import graph, not just diffed lines. SYMBOL-level reinvention (a hand-rolled helper/util/shared component that already exists) is MINIMALISM's beat, not yours -- don't run that grep. When the diff changes an exported/public surface, also judge INTERFACE DESIGN: shape/naming/optionality/ergonomics of the new signature against sibling APIs (principal owns whether it BREAKS consumers; you own whether the shape is right). Structural findings outrank style; at most ONE comment nit per review.
  security    [opus]     -- authz, injection, secrets/keys, trust-boundary input validation, crypto, data exposure.
  correctness [opus low] -- adversarial: null/undefined, edge cases, races, error/reject paths, off-by-one. RESOURCE LEAKS (empirically the #1 real finding class alongside races, and previously uncovered here): handle/stream/connection opened on a path that can throw before close, listener/subscription/interval/timeout registered with no matching removal, useEffect with no cleanup return, DB client or transaction not released on the error branch, unbounded cache/array growth. Name the leaking resource + the path that skips the release.

CONDITIONAL (run only if WHEN holds; else name the skip + reason, one line):
  backend     [sonnet]   -- WHEN a server/API/service is touched. Read the style guide/lint config first. Framework conventions (DI/modules, DTOs + input validation, middleware/guards/filters, ORM/repository), thin controllers (logic in services), no persistence models past the boundary.
  frontend    [sonnet]   -- WHEN UI/client code is touched. Read the style guide first. Reuse shared components before hand-rolling; hooks rules + effect deps; state (no prop drilling, no local state for server data); a11y. Web: design tokens, routing. Native: platform splits, list virtualization, no web-only APIs.
  test        [sonnet]   -- WHEN logic added/changed. Coverage gaps, proving-check adequacy, missing negative/edge tests. Also quality: assertions on implementation detail (not behavior), over-mocking (tests the mock), flaky/time-or-order-dependent, tests that can't fail.
  performance [sonnet]   -- WHEN a data/loop/query/render path touched. N+1, hot paths, complexity, allocations, query/render cost.
  resilience  [opus low] -- WHEN a network/IO/external-call/DB-transaction/money-or-balance op is touched. Failure-path robustness beyond correctness: call w/o timeout; non-idempotent retry (double-charge/write); unbounded/no-backoff retry; multi-step money/state mutation not in a transaction or with no rollback on partial failure; swallowed errors; no degradation when a dependency is down. Name the failing call + what breaks on partial failure.
  migration   [sonnet]   -- WHEN a DB migration/schema/entity-column changes. Deploy-safety: add-column nullable-or-defaulted (never NOT NULL without backfill first); nullable->NOT NULL = backfill THEN constraint, separate steps; drop/rename breaks running code -> stop-using-it deploys before the drop (name the consumer); backfill idempotent + batched on large tables; no big-table-locking DDL; reversible rollback. Verify deploy ORDER (code vs migration) explicitly.
  privacy     [sonnet]   -- WHEN PII/financial data or logging/analytics/error-reporting is touched. PII/financial values (account/routing/balance/SSN/email/phone) in logs, analytics events, error messages, or responses beyond what the caller needs; sensitive op with no audit log; data returned to the wrong tenant/user scope. Name the exact field + sink.
  risk        [sonnet]   -- WHEN the change alters behaviour of an EXISTING live flow (auth/login, money movement, balances, payment/banking-provider calls, tenant or subscription state) or ships a new user-facing path in one of those. Not "is the code correct" (correctness/security own that) and not "does it survive a dependency failing" (resilience owns that) -- this is DEPLOY RISK: if this is wrong in prod, how bad, how do we find out, how do we back out.
                            (1) Reversibility: can it be turned off without a revert+redeploy? Behaviour change to a live money/auth flow with no feature-flag / kill switch -> flag, name the flow. (2) Detectability: would a silent failure surface? New failure mode with no log/metric/alert on the path, or an error swallowed into a generic 500 -> name what breaks invisibly. (3) Blast radius NOW vs later: does it change behaviour for EXISTING users/rows on deploy (retroactive), or only new ones? Retroactive + unflagged is the top finding. (4) Data risk: irreversible write/overwrite/delete with no prior state kept, no backfill-undo. (5) Partial rollout: does old client + new server (or vice versa) hold for the deploy window?
                            Each finding names the specific flow + the concrete bad prod outcome. NO generic "add monitoring" -- if you can't name what goes undetected, it's not a finding. Existing sibling flows ship without a flag too -> that's the repo norm, not a finding (consistency outranks it).

SCALE: the hook measures changed lines + stamps a tier. SMALL DIFF -> principal + clean-arch + minimalism ONLY (security/correctness rarely fire small + cost opus) UNLESS it touches real logic or a trust boundary -> add correctness (+security if authz/secrets/input). FULL DIFF -> the ALWAYS five. CONDITIONALS fire on their WHEN REGARDLESS of tier -- a 5-line migration / new logged PII field / un-timed external call / one-line flip of a live auth branch is small but exactly what migration/privacy/resilience/risk catch. Each critic is a fully-specified read-only leaf; pass the model shown.
